# Implementation Plan: Supabase Egress Optimization & Background Sync Throttling (#global, #sync, #database, #egress)

## Problem & Context
The project is currently on Supabase's Free Tier (5 GB monthly bandwidth limit). In ~2 weeks (Aug 19 – Sep 3), it has consumed **4.11 GB** (82% of quota), with daily consumption peaking between **150 MB and 546 MB per day**. 

Over 90% of this egress is generated by Database/REST API queries rather than Realtime WebSockets or Storage. The primary drivers are:
1. **Unbounded Inventory Polling in `syncManager.js`**: `inventory` is configured with `timestampCol: null`, meaning the background reconciliation engine re-downloads up to 500 rows with `select('*')` every single minute even when no changes occurred.
2. **Aggressive Background Interval**: `SYNC_INTERVAL_MS = 60 * 1000` (60 seconds) runs continuously across 24 tables.
3. **Hyperactive Visibility & Focus Listeners**: Switching browser tabs or windows immediately triggers reconciliation if 3 seconds have elapsed (`MIN_RECONCILE_GAP_MS = 3000`).
4. **Heavy Dashboard Over-fetching in `dashboardRepository.js`**: Re-fetching 500 sales rows with `select('*')` pulls down the heavy JSONB `items` column (which is not needed for overview summary cards) and triggers on every sync completion.

## Proposed Optimizations

### 1. Enable Incremental Delta Sync for Inventory ([`js/data/syncManager.js`](file:///d:/V2BmstzOfficial/js/data/syncManager.js#L29))
- Update `inventory` in `SYNCABLE_ENTITIES` from `timestampCol: null` to `timestampCol: 'updated_at'`.
- This ensures only modified inventory records (`updated_at >= lastSyncedAt - 30s`) are fetched on reconciliation, cutting 99% of recurring inventory bandwidth.

### 2. Increase Periodic Reconciliation Interval ([`js/data/syncManager.js`](file:///d:/V2BmstzOfficial/js/data/syncManager.js#L19))
- Increase `SYNC_INTERVAL_MS` from **60 seconds** to **5 minutes** (`5 * 60 * 1000 = 300000ms`).
- Since live changes are already delivered instantly via Supabase Realtime WebSockets (`broadcast` and `postgres_changes`), background reconciliation serves strictly as an offline catch-up safety net. Running every 5 minutes slashes background polling requests by **80%**.

### 3. Throttle Window Focus & Visibility Change Triggers ([`js/data/syncManager.js`](file:///d:/V2BmstzOfficial/js/data/syncManager.js#L21))
- Introduce a 3-minute throttle (`MIN_VISIBILITY_RECONCILE_GAP_MS = 3 * 60 * 1000`) for `focus` and `visibilitychange` listeners.
- Switching tabs or alt-tabbing rapidly will no longer trigger immediate 24-table cloud queries.

### 4. Optimize Dashboard Sales Queries ([`js/data/repositories/dashboardRepository.js`](file:///d:/V2BmstzOfficial/js/data/repositories/dashboardRepository.js#L308-L310))
- In `syncOwnerDashboardData`, replace `select('*')` on `sales` with only the columns necessary for Overview KPI calculation:
  ```javascript
  .select('id, branch_id, customer_name, amount, cost_amount, gross_profit, created_at, payment, payment_method')
  ```
- This completely excludes the massive JSONB `items` array for 500 records, shrinking sales payload size per dashboard query by ~85%.

### 5. Prevent Redundant Overview Re-Fetch Cascades ([`js/data/syncManager.js`](file:///d:/V2BmstzOfficial/js/data/syncManager.js#L646-L666))
- In `notifyLocalDataChanged()`, only trigger `window.getOwnerDashboardData` if new records were actually applied during reconciliation (`totalRecordsApplied > 0`), rather than on every empty sync cycle.
